# IAM: roles y credenciales


> **🧭 En una mirada**
> - **Qué es:** el uso de credenciales temporales y roles para personas, servicios y CI/CD.
> - **Por qué importa:** evita secretos de larga duración y limita el impacto de una filtración.
> - **Cómo funciona:** una identidad autorizada asume un rol mediante una trust policy.
> - **Para qué se usa:** dar acceso seguro a EC2, ECS, Lambda, pipelines y otras cuentas.

## Credenciales de larga duración

Las access keys de usuarios IAM son credenciales de larga duración. Deben evitarse para aplicaciones, servidores y CI/CD. Si son inevitables, deben almacenarse en un gestor seguro, rotarse y tener permisos mínimos.

## Credenciales temporales

STS entrega credenciales temporales al asumir un rol. Incluyen access key, secret key y session token, y expiran.

Son preferibles porque:

- Reducen la ventana de exposición.
- Permiten separar permisos por workload.
- Se pueden emitir mediante federación o roles de servicio.

## Roles de servicio

Un servicio AWS asume un rol mediante su trust policy. Ejemplos:

- ECS task role: permisos que necesita el código de la aplicación.
- ECS task execution role: permisos para descargar imágenes y enviar logs.
- Lambda execution role: permisos de la función.
- EC2 instance profile: permisos de procesos ejecutándose en la instancia.

No confundas los permisos del runtime con los permisos necesarios para arrancar el workload.

## CI/CD

La opción recomendada es federar GitHub Actions u otro proveedor con OIDC y permitir que asuma un rol limitado. No guardar access keys permanentes como secrets si puede utilizarse federación.

## Regla para Paideia

Cada microservicio debe tener un rol independiente. `content-service` puede acceder a S3, pero `course-service` no debe heredar ese permiso solo porque ambos se ejecuten en ECS.
