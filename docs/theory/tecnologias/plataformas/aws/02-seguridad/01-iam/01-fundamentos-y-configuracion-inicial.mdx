# AWS IAM: fundamentos y configuración inicial


> **🧭 En una mirada**
> - **Qué es:** el servicio de identidad y acceso que decide quién puede hacer qué.
> - **Por qué importa:** los permisos excesivos y las credenciales expuestas son riesgos críticos.
> - **Cómo funciona:** principales, políticas, roles y condiciones se evalúan con denegación explícita prioritaria.
> - **Para qué se usa:** proteger personas, servicios, automatizaciones y acceso entre cuentas.

> Ruta: AWS Practitioner → IAM
>
> Objetivo: entender quién puede hacer qué en AWS y preparar una cuenta de laboratorio sin utilizar credenciales permanentes ni el usuario root para el trabajo diario.

## 1. Qué problema resuelve IAM

IAM (*Identity and Access Management*) controla el acceso a los recursos de AWS.
La pregunta fundamental es:

```text
¿Quién puede realizar qué acción sobre qué recurso y bajo qué condiciones?
```

Una autorización se puede expresar así:

```text
Principal + Action + Resource + Condition
```

Ejemplo conceptual:

```text
El rol course-service puede leer objetos del bucket de cursos,
pero no puede eliminar el bucket ni acceder a otros buckets.
```

## 2. Conceptos esenciales

## 🧩 Identidades humanas y workloads

| Necesidad | Identidad preferida | Motivo |
|---|---|---|
| Persona trabajando en consola | IAM Identity Center | SSO y credenciales temporales |
| Aplicación en ECS | Task role | Permisos asociados al workload |
| Función Lambda | Execution role | Acceso temporal a servicios |
| CI/CD externo | Rol federado con OIDC | Sin access keys permanentes |
| Integración antigua | Usuario IAM con access key | Solo como excepción controlada |

> **✅ Regla práctica:** si una aplicación necesita una access key guardada en una variable de entorno, detente y revisa si puede utilizar un rol de servicio.

### Cuenta raíz (root user)

Es la identidad con máximo privilegio de la cuenta AWS. Debe utilizarse únicamente para tareas que requieren root, por ejemplo algunas operaciones iniciales de la cuenta.

Buenas prácticas:

- Activar MFA inmediatamente.
- No crear access keys para root.
- No utilizar root para desplegar aplicaciones.
- No compartir sus credenciales.

### Principal

La identidad que realiza una llamada a AWS. Puede ser:

- Un usuario IAM.
- Un rol IAM asumido temporalmente.
- Un servicio de AWS.
- Otra cuenta o identidad federada.

### Usuario IAM

Representa una identidad de larga duración dentro de una cuenta. Puede tener credenciales de consola o access keys.

Para trabajo moderno se prefieren identidades federadas y roles con credenciales temporales. No se deben crear usuarios IAM individuales por cada aplicación.

### Grupo IAM

Agrupa usuarios y facilita asignar permisos comunes. No es una identidad que pueda asumir un rol.

### Rol IAM

Es una identidad que puede ser asumida temporalmente por un usuario, un servicio o una identidad externa. Es la opción habitual para:

- ECS, EC2 y Lambda.
- GitHub Actions u otros sistemas CI/CD.
- Acceso entre cuentas.
- Acceso humano mediante IAM Identity Center.

Un rol tiene dos políticas distintas:

1. **Trust policy**: quién puede asumirlo.
2. **Permissions policy**: qué puede hacer después de asumirlo.

### Política IAM

Documento JSON que permite o deniega acciones. Sus elementos principales son:

- `Effect`: `Allow` o `Deny`.
- `Action`: acciones como `s3:GetObject`.
- `Resource`: ARN del recurso afectado.
- `Principal`: quién está incluido, principalmente en políticas de confianza o políticas basadas en recursos.
- `Condition`: restricciones adicionales.

Ejemplo didáctico — no usarlo como política universal:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::NOMBRE_DEL_BUCKET/cursos/*"
    }
  ]
}
```

## 3. Cómo se evalúan los permisos

La regla mental más importante es:

```text
Deny explícito > Allow > ausencia de Allow
```

Por defecto, el acceso se deniega. Un `Allow` puede concederlo, pero cualquier `Deny` explícito aplicable lo vuelve a denegar.

También hay que distinguir:

- **Identity-based policy**: asociada a un usuario, grupo o rol.
- **Resource-based policy**: asociada al recurso, por ejemplo un bucket S3.
- **Permission boundary**: límite máximo de permisos de una identidad.
- **Service Control Policy**: restricción de AWS Organizations.
- **Session policy**: límite adicional de una sesión temporal.

Para Practitioner, primero domina usuarios, roles, policies, MFA, least privilege y el modelo de evaluación. Los límites avanzados pueden estudiarse después.

## 4. Configuración inicial segura de una cuenta personal

Realizar estos pasos desde la consola de AWS:

### Paso 1: proteger root

1. Iniciar sesión como root.
2. Activar MFA, preferentemente una aplicación autenticadora.
3. Confirmar que no existen access keys de root.
4. Guardar las credenciales de recuperación fuera del repositorio y del equipo compartido.
5. Cerrar sesión.

### Paso 2: activar control de costes

1. Revisar el Free Tier y el pricing vigente de cada servicio.
2. Crear un AWS Budget mensual con alertas de coste.
3. Configurar alertas de uso si están disponibles para el servicio que se está estudiando.
4. Eliminar recursos de laboratorio al terminar cada práctica.

El Free Tier no significa que todo recurso sea gratuito. NAT Gateway, IPs públicas, balanceadores, bases de datos y almacenamiento pueden generar costes.

### Paso 3: crear acceso humano con IAM Identity Center

Para una cuenta nueva, la opción preferida para el acceso diario es IAM Identity Center:

1. Abrir IAM Identity Center desde la consola.
2. Activar la instancia de organización si AWS lo solicita.
3. Crear un usuario de laboratorio con un correo controlado por ti.
4. Activar MFA según la configuración disponible.
5. Crear un permission set administrativo únicamente para el laboratorio inicial.
6. Asignar ese permission set a tu cuenta.
7. Probar el acceso desde el portal de AWS.

En una organización real se empezaría con permisos menores. Para una cuenta de aprendizaje, el permission set administrativo permite avanzar al inicio, pero debe reemplazarse por permisos específicos conforme aparezcan los laboratorios.

### Paso 4: configurar la CLI sin access keys permanentes

Instalar AWS CLI v2 y comprobar la instalación:

```powershell
aws --version
```

Configurar un perfil mediante IAM Identity Center:

```powershell
aws configure sso --profile paideia-lab
```

La orden solicitará el portal SSO, región, cuenta, rol y formato de salida. No introducir secretos en archivos del proyecto.

Validar la sesión:

```powershell
aws sso login --profile paideia-lab
aws sts get-caller-identity --profile paideia-lab
```

La salida debe identificar la cuenta y el rol que estás utilizando. No publicar esa salida junto con información sensible.

Para evitar errores por usar otro perfil:

```powershell
$env:AWS_PROFILE = "paideia-lab"
aws sts get-caller-identity
```

## 5. Laboratorio IAM para Paideia

El primer laboratorio debe ser pequeño y reversible. No empezar todavía con todos los microservicios.

### Objetivo

Crear una política que permita leer objetos de un único bucket de laboratorio y comprobar que:

- La acción permitida funciona.
- Una acción no incluida falla.
- Un recurso diferente falla.
- La identidad que realiza la llamada es el rol esperado.

### Ejercicio conceptual

Diseñar una política para un futuro `content-service`:

```text
Permitido:
  s3:ListBucket sobre el bucket de contenido
  s3:GetObject sobre contenido/*

No permitido:
  s3:DeleteObject
  s3:PutObject
  acceso a otros buckets
```

Antes de aplicarla:

1. Sustituir los nombres de ejemplo por recursos reales.
2. Revisar la política con IAM Access Analyzer o el simulador de políticas.
3. Probar primero en un entorno de laboratorio.
4. Eliminar el bucket y los objetos al terminar si ya no son necesarios.

## 6. Relación con Paideia

Más adelante, cada componente debería utilizar una identidad distinta:

| Componente | Identidad AWS futura |
|---|---|
| `content-service` | Rol de tarea ECS con acceso limitado a S3 |
| `course-service` | Rol de tarea ECS sin permisos sobre S3 si no los necesita |
| CI/CD | Rol federado de despliegue, no access key guardada en GitHub |
| ECS | Roles separados de ejecución y de tarea |
| Terraform | Rol de aprovisionamiento con permisos controlados |

La regla clave es que un servicio no debe recibir permisos porque “podría necesitarlos”. Debe recibir únicamente los permisos necesarios para su responsabilidad.

## 7. Errores frecuentes

- Usar root para tareas diarias.
- Crear access keys y dejarlas en `.env`, código o repositorios.
- Asignar `AdministratorAccess` a todas las aplicaciones.
- Utilizar `Resource: "*"` sin una justificación.
- Confundir la trust policy con la policy de permisos.
- Permitir acceso público a S3 para evitar problemas de permisos.
- No activar MFA.
- No crear alertas de costes.
- No borrar recursos de laboratorio.

## 8. Checklist de finalización

- [ ] Root tiene MFA.
- [ ] Root no tiene access keys.
- [ ] Existe un presupuesto con alertas.
- [ ] Existe un usuario de laboratorio en IAM Identity Center.
- [ ] La CLI funciona mediante el perfil `paideia-lab`.
- [ ] `aws sts get-caller-identity` devuelve la cuenta esperada.
- [ ] Puedes explicar usuario, grupo, rol, policy y principal.
- [ ] Puedes explicar la diferencia entre trust policy y permissions policy.
- [ ] Has probado un `Allow` y un `AccessDenied` deliberado.
